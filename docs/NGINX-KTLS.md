# Kernel TLS opt-out (`_NGINX_KTLS`)

## What KTLS is

Kernel TLS (kTLS) moves TLS record encryption/decryption from OpenSSL in
userspace into the Linux kernel. BOA builds nginx against an OpenSSL that has
kTLS compiled in and turns it on with `ssl_conf_command Options KTLS;` in every
HTTPS server block. When the kernel and NIC cooperate it can raise static-file
throughput modestly (roughly 8–16% on Linux for large cached responses); on a
typical Drupal / image workload the gain is small.

## The symptom

On OpenSSL 3.2 and later the kernel kTLS receive path returns
`recv() failed (5: Input/output error)` and logs it at `[alert]` whenever a TLS
*control* record — an alert, a handshake message, or a TLS 1.3 KeyUpdate —
arrives on a connection where nginx did not supply a control-message buffer
(nginx issue 651). The connection is aborted.

In practice most of these are harmless: they land on connection teardown and on
bot / scanner traffic receiving small error responses (the client already has,
or does not care about, the body). The visible cost is `[alert]`-level log
spam that survives `error_log crit` and can bury other alerts. There is a
theoretical tail where a long-lived TLS 1.3 connection that rekeys mid-response
could truncate a large body, and the same kernel code path carries a 2025 local
privilege-escalation CVE (`CVE-2025-39682`) — so a server-wide off switch is
worth having even though the day-to-day effect is noise.

## The lever

`_NGINX_KTLS` in `/root/.barracuda.cnf`:

- **`YES` (default)** — KTLS stays on everywhere. No change from historical
  behaviour; you do not need to set anything.
- **`NO`** — KTLS is disabled server-wide on the next `barracuda up-*`.

Setting `NO` makes BOA write the control file `/etc/nginx/no_ktls.conf`. Three
things read it, so every KTLS emitter goes dark together:

- the Ægir/provision nginx service leaves `nginx_has_ktls` **false** (the same
  mechanism `basic_nginx.conf` uses for config mode), so all four SSL vhost
  templates omit the KTLS directive with no template change;
- the static wildcard-SSL front (`pre.d/nginx_wild_ssl.conf`) has its KTLS line
  stripped on deploy;
- the per-domain `z_<domain>_ssl_proxy.conf` fronts have theirs stripped when
  they are (re)generated by `xoct` / `xcopy`.

The wild-SSL refresh gate and the per-domain ssl_proxy self-heal loop are aware
of the control file, so toggling the value settles cleanly in either direction
instead of fighting itself.

## Disable KTLS on a box

Substitute your tier verb: `up-lts` (free LTS), `up-pro` (PRO), or `up-dev`.

```bash
echo '_NGINX_KTLS=NO' >> /root/.barracuda.cnf
barracuda up-<tier> system
```

Re-enable by removing the line and upgrading again:

```bash
sed -i '/^_NGINX_KTLS=/d' /root/.barracuda.cnf
barracuda up-<tier> system
```

## Verify

```bash
# Should be empty when disabled, and list every HTTPS front when enabled.
nginx -T 2>/dev/null | grep 'Options.*KTLS'

# The control file mirrors the setting.
ls -l /etc/nginx/no_ktls.conf   # present only when _NGINX_KTLS=NO

# Watch the alert rate before/after on a box that shows it.
grep -c 'recv() failed (5: Input/output error)' /var/log/nginx/error.log
```

When to disable: a box on OpenSSL 3.2+ whose `error.log` is dominated by the
`recv() ... (5: Input/output error)` alert, or where you want the CVE-hardening
posture. Leave it on (default) otherwise — the throughput it buys is real, if
small, and the alert is usually just noise.
