# XDR9000: The Permanent On-Box Health & Attack Archive

A BOA box detects attacks and heals its own services around the clock — and
then, until now, routinely destroyed the records: ban ledgers are reaped
within hours, incident logs rotate, and the major-OS-upgrade path wipes
`/var/log/boa/*.log` entirely. XDR9000 closes that gap. It is a read-only
harvester that copies those records into a permanent, append-only archive
*before* their reapers run, plus a root-only CLI that renders the whole
history with one command.

It observes only: nothing is banned, killed, restarted or reconfigured by
it. Recording is **on by default** on every installed hosting box running
the monitor stack; the `xdr9000` reader lands on every class of box.

## What is recorded

- **Attack events** from the web, SSH and FTP ban ledgers
  (`scan_nginx.archive.log`, `hackcheck.archive.log`,
  `hackftp.archive.log`) — offending IP, hit count, timestamp.
- **Auto-heal and incident events** from thirteen subsystem incident logs
  (high.load, oom, nginx, mysql, mysql.backup, php, valkey, redis,
  unbound, java, system, batch_guard, task_guard) plus i18n flood alerts, segfault
  alerts, SQL-watch kills and convert kills.
- **Backup outcomes**: every `/var/log/boa/*.archive.log` is harvested, so
  backup results outlive the upgrade-path log wipe.
- **Metric samples**, roughly every 5 minutes: load averages, available
  memory, swap, disk use for `/` and `/data`, the current load tier,
  network counters and deltas, SYNPROXY packet counts, csf deny/tempban
  counts. Counter deltas are reset-floored, so a csf reload records a 0
  delta rather than a bogus spike.
- **Box facts**, hourly: kernel, CPU count, RAM, swap, per-mount disk,
  uptime, and a service up/down verdict list matching `boa info` exactly.
- **Metric corpora preserved verbatim**: the fpm-tune, sqlprobe and
  load-profile per-day streams are copied into the archive, so their data
  outlives the corpora's own 30/30/14-day retention windows. On first
  deployment the copy gradually backfills whatever days each corpus still
  holds, bounded per pass.

## Where it lives, and for how long

The archive is JSONL under `/var/log/boa/xdr9000/`: per-day event files
(`YYYY/MM/events-YYYYMMDD.jsonl`), per-day samples, and a one-line-per-day
rollup spine (`rollup.jsonl`). The directory is mode 700, root-only. It
deliberately sits in a subdirectory so it survives the major-OS-upgrade
`rm -f /var/log/boa/*.log` wipe, and it matches no logrotate glob.

The archive is permanent by construction: the engine only ever appends.
Event and sample files from past months are compressed with `gzip -9`;
`rollup.jsonl` is never compressed and never pruned. **Nothing is ever
deleted, so budget the path into disk-space expectations on long-lived
boxes.**

## Reading it: the xdr9000 CLI

Root-only, read-only, transparent about gzip-compressed past months:

```sh
xdr9000 status            # archive health, first record, size, engine state
xdr9000 today             # today's events and samples
xdr9000 attacks --days 30 # per-vector totals, unique IPs, top offenders
xdr9000 heals --days 30   # incident counts per subsystem
xdr9000 report            # full report incl. since-first-record totals
xdr9000 json events       # raw JSONL feed (windowed; json rollup = whole spine)
```

Defaults: 7 days for `attacks`/`heals`, 30 for `report`. The
since-first-record totals in `report` come from the daily rollup, so they
become meaningful from the second day of recording onward — a freshly
upgraded box starts recording immediately and grows a history over the
following days; the attack and incident streams do not backfill.

## Cost and control

The engine renices itself to background priority, reads at most 1 MiB per
source per pass (carrying the remainder forward), holds a single-instance
lock, throttles samples to ~5 minutes and box facts to ~1 hour, and does
the rollup plus month-end compression once per date change. It reads only
complete lines and tracks position by inode plus byte offset, so log
rotation or truncation resets cleanly and half-written lines wait for the
next pass. It harvests the `*.archive.log` ledgers rather than the live
ban queues, so it never races the ban-log reapers; losses ahead of them
are bounded to roughly one harvest pass.

`_XDR9000=NO` in `/root/.barracuda.cnf` stops all recording passes while
leaving every byte already archived untouched; `xdr9000 status` then
reports the engine OFF with the archive kept. Any other value (or no
entry at all) means recording is on. `bash
/var/xdrago/monitor/check/xdr9000.sh --force` runs all three passes on
demand, bypassing the throttles — useful for validation.

## Delivery scope

The recording engine (`xdr9000.sh`) is delivered to installed hosting
boxes running the monitor stack, and launches from the monitor fan-out.
The `xdr9000` CLI is delivered to every class of box and symlinked at
`/usr/local/bin/xdr9000`; on a box the engine has never run on, it exits
with a clear message saying so.
