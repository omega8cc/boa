We are pleased to inform you that your Ægir instance has been successfully upgraded to [boa.version]

This is the Centaur release, named for two natures in one body. Your control panel could already upgrade a Drupal 10 or later site onto a newer platform and keep the way back, but somebody still had to build that newer platform first. Now the panel builds it too, checks that it really is a newer version of the same code, and moves the site, all in one task. Beside that come security updates for Drupal 7, Pressflow 6 and Grav platforms, a current Adminer, and PHP that finds its files faster.

----------------------------------------
BUILD A NEWER VERSION OF A PLATFORM
----------------------------------------

Open a platform the panel built with Composer, on Drupal 10 or newer, and you will find a new button, Build newer version. It builds the platform again into a new folder beside the old one, the same way the panel built it the first time, at the version you pick. A plain Drupal platform, built from Drupal's own project template, offers the newest patch release, the newest minor release or the next major release (Drupal 11 from Drupal 10; Drupal 12 is not offered yet); any package takes a version you type; your own repository takes another branch or tag. When the build is done the panel judges it, and the new platform is kept only if it is a newer version of the same codebase. Nothing changes on the old platform or its sites meanwhile; a kept platform simply appears as a choice in their Upgrade. The guide is at https://docs.boa.io/using/deploying-code/building-a-newer-version

----------------------------------------
UPGRADE A SITE BEFORE ITS NEW PLATFORM EXISTS
----------------------------------------

The Upgrade dialog of a site has a new last choice: build a newer version of the platform first. Choose it and one task does the whole job in order. It checks what can be known beforehand (disk space, time, the PHP the newer Drupal asks for), builds the platform, judges it, then copies your site as the way back and moves it, exactly as an Upgrade always does. Nothing of the site is copied or moved before the build is kept, so a build that fails or is not kept leaves the site as it was. A build that is kept stays as a platform even when the site could not move this time, ready for the next try and for the other sites of the old platform. See https://docs.boa.io/using/deploying-code/upgrading-with-a-build

----------------------------------------
A WHOLE PLATFORM'S SITES IN ONE GO
----------------------------------------

Upgrade all sites, the platform task that upgrades every ready site of a platform one at a time, has the same choice. It builds the newer platform once, and when the build is kept it moves the sites onto it, each as its own Upgrade with its own way back. If the build is not kept, no site is touched.

All of this belongs to the account's main login, like Upgrade and Go back; team members with the client, site operator or platform manager role do not see it.

----------------------------------------
YOUR LIMITS STILL DECIDE
----------------------------------------

The line in a platform's control file that limits which upgrades it accepts, drupal_upgrade_modes, now governs builds too: the dialog offers only what the line allows, a finished build the line refuses is not kept, and a kept build carries the line on. When a newer platform brings a security advisory the old one did not have, the Upgrade no longer refuses flatly: it names the advisory in its plan and its result and goes ahead, unless your line accepts security fixes only.

----------------------------------------
BUILDS THAT EXPLAIN THEMSELVES
----------------------------------------

A platform built from your own Git repository on a server your account has not used before now builds at the first try: the server's key is stored at first contact, and a changed key is refused later. A build that fails inside Composer now shows Composer's closing lines at full width, where narrow wrapping used to push the line that names the cause out of sight. And a build step that hangs is stopped after 45 minutes and cleaned up.

----------------------------------------
THE UPGRADE TASK, WISER AFTER REAL USE
----------------------------------------

The Upgrade task that arrived with the last release has been through real use since. It now tells codebases apart, so a site on a plain Drupal platform is not offered a distribution such as Drupal CMS as its newer version. It offers a site on a finished Drupal release only finished releases, never a beta or a release candidate. A site that an earlier, interrupted upgrade left something in the way of is shown as not ready, with the reason. And the dialog numbers its steps.

----------------------------------------
YOUR OWN LOOK STILL COUNTS
----------------------------------------

After a move the panel looks at two simple things: whether Drupal's database updates completed, and whether the site's home page and login page respond as they used to. It runs no tests of your own and it has no staging step, so for an upgrade that matters, clone the site and upgrade the clone first. We are only starting here. Steps like these may join the panel later, with no dates promised, and the aim is clear: looking after a site's whole life almost the way continuous integration does, in a human-friendly way, where the panel's checks help your own testing and blind automation never takes its place. What the two checks cover is at https://docs.boa.io/using/deploying-code/upgrading-a-site#what-checked-means-and-what-it-does-not

----------------------------------------
A NOTICE WHEN A SITE FALLS BEHIND
----------------------------------------

Drupal publishes security fixes only for its newest release lines. Your server can now tell you by mail, once for each site, when a Drupal 10 or later site of yours runs a release that no longer gets them. The notice is switched on by whoever runs the server, so ask your host if you would like it. What it says, and when, is at https://docs.boa.io/using/deploying-code/nightly-upgrade-report

----------------------------------------
EVERY DRUPAL LINE, AND GRAV
----------------------------------------

New Drupal 10 and 11 platforms are built on Drupal's security releases of 25 November: 10.6.23, 11.3.23 and 11.4.14. New Drupal 7 platforms are built on core 7.108.2, whose session handling is ready for PHP 8.6, and new Pressflow 6 platforms on 6.60.5, where a logout no longer ends in an error page on PHP 8. New Grav platforms are built on Grav 2.2.35, a security release, and the Upgrade Grav task brings an existing Grav site to it.

----------------------------------------
PAGES THAT COST LESS
----------------------------------------

PHP checks every file a request opens against a list of folders it may read. The list has not changed, but it is now sorted in the order requests use it, and on a test server that alone took about a fifth off the processor time of a cached page and of the panel's own pages. Your sites have it already; there is nothing to switch on.

----------------------------------------
IN YOUR SHELL
----------------------------------------

vdrush @site updb runs again on a Drupal 10 or newer codebase after a Composer run has put Drush's own launcher back. dr finds its site when the address comes from a variable, as in a Composer script or a Git alias, and a Drush line with an option like --uri=$uri runs. Your command history survives a script or a single remote command.

----------------------------------------
EVERYDAY TASKS, STEADIER
----------------------------------------

A Backup or a Clone no longer fails on a file or folder one of your shell users closed to others inside a site's files. A task that runs inside another, such as the Verify at the end of a Clone, is no longer turned away as busy by its own parent. While your account is being upgraded, the tasks of a platform that runs on its own command-line PHP now wait for the upgrade to end, where they used to fail. And the database browser at /sqladmin/ is Adminer 6.3.1.

Everything else this release changed, with the versions and the reasons, is at https://docs.boa.io/releases/boa-5-88-899
