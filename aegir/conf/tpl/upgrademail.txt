This is the Dragon release. Its main gift sits in your control panel: a site on Drupal 10 or later can now be moved onto a newer platform with one task that keeps the way back open, so trying a new core or a new set of modules no longer means risking the site you have. Around it, the release makes tasks start sooner, serves crawlers from the cache on more sites, and lets off-site backups run side by side. This month's security releases of PHP and Nginx are already on your server.

----------------------------------------
UPGRADE A SITE, KEEP THE WAY BACK
----------------------------------------

Open a Drupal 10 or later site in the panel and you will find a new task, Upgrade. Pick a newer platform from the list and the task does two things in order: it makes a copy of the site exactly as it is, switched off and kept beside the original, and then it moves the site onto the platform you chose. If the database updates do not run to their end, or the site's home or login page no longer answers as it should, the move undoes itself and the site stays where it was. The list offers only platforms the site can really move up to, and Drupal 12 is not offered as a target yet. Each Drupal 10 or later site's page gains a line, Drupal updates, that says whether an upgrade is available and onto which platform, or why none is ready, and one line in the site's or the platform's control file limits which kinds of upgrade a site accepts. The task belongs to the account's main login; team members with the client or site operator role do not see it.

----------------------------------------
WHAT CHANGES COMPARED WITH MIGRATE
----------------------------------------

Until now a site reached newer code through Migrate, and Migrate stays exactly where it is. For an upgrade, though, it left the safety in your hands. The way back was a clone you had to remember to make before the move. When Drupal's database updates stopped half-way, Migrate reported a warning and the site was already on the new platform. And returning to the old one meant taking the moved site out of the way, renaming your clone into its place and setting up cron, HTTPS and aliases on it again, because a Migrate back is refused once a module's database has moved up.

Upgrade does all of that for you, and adds a check Migrate never had: it opens the home page and the login page before and after the move, and undoes the move when they no longer answer the same. It also lists only platforms that are a real step up for the site. Keep Migrate for what Upgrade does not do: sites on Drupal 9 or older and on Backdrop, renames, and any upgrade you want to rehearse on a clone first, since Upgrade has no test stage and works on the live site.

----------------------------------------
GO BACK, IF YOU NEED TO
----------------------------------------

The copy an Upgrade kept is not just a backup file. A second new task, Go back, switches the upgraded site off, sets it aside under another name and puts the copy back under the site's own name, with its aliases, redirection and HTTPS setting. The site page shows how old the copy is and how much disk it takes, so you can decide when you no longer need it. If a Go back is interrupted, running it again finishes the job from where it stopped.

----------------------------------------
SEE WHAT A SITE HAS PENDING
----------------------------------------

Check available updates is a third new task, and it changes nothing: it writes into its task log the known security problems of the code a site runs, for Drupal 6 and 7 as well as for Drupal 8 and later. It replaces the old health check, which had stopped doing anything useful, and it is the quick read before you plan an Upgrade.

----------------------------------------
A PHP VERSION THAT BELONGS TO THE PLATFORM
----------------------------------------

Until now a site took its web PHP version from the account, in fpm.info, or from a line of its own in multi-fpm.info. Both follow the site, never its code: when a platform needed a newer PHP, every site you moved onto it wanted a line of its own. A platform can now carry the version itself. Add one line to ~/static/control/fpm-per-platform.info, the platform's folder and the version:

  d11-prod 8.4

Every site on that platform is then served by PHP 8.4, and a site that arrives there through Upgrade, Migrate or Clone switches to it in the same step. A site with its own line in multi-fpm.info keeps it, so one site can still stay behind. The file is for the web only: drush, composer and your Ægir tasks keep their own setting in cli-per-platform.info. A change takes effect within a few minutes, and a line that cannot apply is named, with the reason, in a file beside yours. It needs an account that serves its sites on more than one PHP version; the guide is at https://docs.boa.io/using/tuning/php-version

----------------------------------------
SPEED BOOSTER FOR SHOPS, AND ONE COPY PER COUNTRY
----------------------------------------

Speed Booster, the cache in front of your sites, learned two things. A shop, or any site that starts a session for every visitor, could not have its pages stored, so every crawler request was rendered from scratch; crawlers that send no cookie now get such pages from the cache, and your visitors notice nothing but a calmer site. And a site that prices or words its pages by country can keep one cached copy per visitor country, where one country's page used to be all the cache could hold. The per-country copies are switched on per site by whoever runs the server: ask your host, and see https://docs.boa.io/using/caching/front-cache-and-page-cache

----------------------------------------
DRUPAL 12 AND DRUSH 15 ARE EXPECTED
----------------------------------------

Drush 15 no longer brings its own launcher; it runs under the command Drupal core ships, dr. BOA is ready for that on both sides. In the panel, a site on a codebase with Drush 15 installs and takes its database updates like any other; a codebase with no Drush at all installs its sites too, but the panel skips their database updates and says so in the task log. In your shell, on Drupal 11.5 and newer, run dr --url=https://your-site.example status from the folder of the codebase that holds vendor, while the platform is unlocked. Drupal 12 platforms are built with Drush 15 from Drupal 12's first release.

----------------------------------------
PHP 8.6 IN FULL
----------------------------------------

PHP 8.6 has left its release candidates behind: the final 8.6.0 is here with the Valkey cache, upload progress and YAML modules working on it, so PHP 8.5 or 8.6 are both real choices where your server offers them.

----------------------------------------
TASKS THAT START SOONER AND SAY MORE
----------------------------------------

A task you queued no longer waits for minutes behind a site's cron run, and a task held back by another running task says so on its own page. Building a platform from the panel now stops at the first step that fails, cleans up after itself and names the folder it could not write, where it used to carry on and leave a half-built platform behind. The Add platform form refuses a path another platform already uses, the Migrate form no longer shows dozens of upgrades between two identical platforms, and every confirm screen describes its task.

----------------------------------------
FEWER SURPRISES
----------------------------------------

Background batch jobs that a Drupal site starts over HTTPS run to their end instead of stopping part way, a site renamed on its own platform answers at once under the new name, and a change you make with Drush no longer leaves the web pages on an old cached copy.

----------------------------------------
BACKUPS THAT RUN SIDE BY SIDE
----------------------------------------

If you keep your own off-site backups, they no longer stand in a queue behind the server's backup, two accounts' backups now run at the same time, and a restore you queue with mybackup starts as it should. Restoring the same folder a second time puts the new copy beside the first one, and a retention you set in days or weeks is honoured, where it used to fall back to three months.

----------------------------------------
WHEN A SERVER MOVES
----------------------------------------

Should your instance ever move to new hardware, the messages you receive now say where the control panel is afterwards, where SSH and SFTP logins connect, which bucket of your own off-site backups changes its name and which address your sites' outgoing requests come from. A login on the old server tells you where the account went, in case a saved connection still points there.

Curious about the details? The full story of this release is at https://docs.boa.io/releases/boa-5-88-888
